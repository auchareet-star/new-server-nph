โรงพยาบาลต้องตัดสินใจอะไรบ้าง?

รายการการตัดสินใจที่ต้องการคำตอบก่อนเริ่ม Migration

จำเป็น เลือกวันและช่วงเวลา Maintenance Window สำหรับการย้ายระบบ

ระบบ HAOS จะ ไม่สามารถใช้งานได้ประมาณ 4–8 ชั่วโมง ในช่วงย้าย ต้องเลือกช่วงที่กระทบน้อยที่สุด

แนะนำ
วันศุกร์ดึก หรือวันเสาร์เช้า
ผู้ป่วย Out-patient น้อย, เจ้าหน้าที่สามารถใช้ระบบ Offline ชั่วคราวได้
ทางเลือก
วันหยุดนักขัตฤกษ์
ขึ้นอยู่กับปฏิทินผู้ป่วย ต้องตรวจสอบว่าไม่มี OPD ขนาดใหญ่
⚠️ ต้องแจ้งทีม Clinical ล่วงหน้าอย่างน้อย 2 สัปดาห์ เพื่อเตรียมแผนรองรับ (Downtime Procedure)
จำเป็น ระบุผู้ประสานงาน IT ที่จะทดสอบและ Sign-off หลังย้าย

หลังย้ายเสร็จ ทีม AYD จะทดสอบระบบร่วมกับ IT โรงพยาบาล ก่อน Go-live จริง ต้องมีคนจากโรงพยาบาลที่:

  • เข้าใจ Workflow ของ HAOS HIS เพียงพอที่จะยืนยันว่าระบบทำงานถูกต้อง
  • มีสิทธิ์ตรวจสอบข้อมูลผู้ป่วย เพื่อทดสอบว่าข้อมูลครบและถูกต้อง
  • สามารถประสานงานกับฝ่าย Clinical ได้ในกรณีที่พบปัญหาหลังย้าย
✅ โดยปกติคือ IT Admin หรือ HIS Coordinator ของโรงพยาบาล — ต้องการชื่อและเบอร์ติดต่อ
ต้องเลือก Server เก่า (Bare Metal เดิม) จะเก็บไว้เป็น Standby กี่เดือน?

หลังย้ายสำเร็จ แนะนำให้เก็บ Server เก่าไว้เพื่อความมั่นใจ ในกรณีที่เกิดปัญหาไม่คาดฝัน สามารถ Rollback ได้ภายใน 4 ชั่วโมง

แนะนำ
เก็บไว้ 3–6 เดือน
ปิดไว้แต่ไม่ถอดออก — พร้อม boot ได้ทันทีถ้าฉุกเฉิน
ประหยัดพื้นที่
เก็บ 1 เดือน แล้วนำไปใช้งานอื่น
ความเสี่ยงสูงกว่า ถ้าพบปัญหาช้าอาจ rollback ไม่ทัน
รับทราบ รับทราบว่า VMware ESXi คือ Platform ที่เลือกใช้

ทีม AYD เลือกใช้ VMware ESXi เพราะ:

  • มี License vSphere 7 Enterprise Plus อยู่แล้ว — ไม่หมดอายุ (Never expiry) ครอบคลุม feature ระดับ Enterprise
  • รองรับ VM ทุกตัวที่ต้องการ — HA, vMotion, Storage vMotion พร้อมใช้
  • Outsource รับผิดชอบ compatibility กับ Hardware SR650 V4 และการติดตั้ง
📌 โรงพยาบาลไม่ต้องตัดสินใจเรื่องนี้ใหม่ — แค่รับทราบว่านี่คือแนวทางที่เลือกไว้แล้ว

คำถามที่ 3

จะมีปัญหากับแผนย้ายเครื่องไหม?

ความเสี่ยงที่มีอยู่จริง และสิ่งที่วางแผนรองรับไว้แล้ว

💾
ข้อมูลผู้ป่วยไม่หาย
SQL Database ย้ายด้วย Backup/Restore — ตรวจสอบ record count และ checksum ก่อน cutover
⏸️
ระบบ down 4–8 ชั่วโมง
เป็น planned downtime — ต้องวางแผน downtime procedure ร่วมกัน และแจ้งล่วงหน้า 2 สัปดาห์
🚀
ระบบเร็วขึ้นหลังย้าย
แก้ I/O contention บน shared disk — คุณหมอและพยาบาลจะรู้สึกได้ถึงความเร็วที่ดีขึ้น

ตารางความเสี่ยงและแผนรองรับ

ความเสี่ยง ระดับ อธิบาย แผนรองรับ
ข้อมูลสูญหาย ต่ำมาก SQL ย้ายด้วย Backup/Restore มีการตรวจสอบ checksum และ record count ก่อน cutover Backup full ก่อนเริ่มทุกครั้ง, verify ก่อน cut
ย้ายแล้วระบบช้าลง ต่ำ Hardware ใหม่ Lenovo + NVMe + RAM 240 GB จาก 160 GB เดิม — ทุกปัจจัยชี้ไปที่ "เร็วขึ้น" Rollback กลับ server เก่าได้ทันทีถ้าพบปัญหา
การ Convert VM ล้มเหลว ปานกลาง VMDK → VHDX ต้องใช้ StarWind V2V และทดสอบก่อน — โอกาสเกิดปัญหาทางเทคนิคมีบ้าง แต่จัดการได้ ทำ test run ก่อน production cut — SQL ใช้ Backup/Restore หลีกเลี่ยง convert
Downtime นานกว่าคาด ปานกลาง ถ้าพบปัญหาระหว่างย้าย อาจต้องขยาย window — ต้องวางแผน buffer เวลาไว้ เริ่มช่วงดึก, วางแผน 12 ชั่วโมง แม้คาดว่า 8 ชั่วโมงก็พอ
Hyper-V Host ล่มหลังย้าย ต่ำ Single server = ทุก VM down ถ้า Host มีปัญหา — แต่นี่คือข้อจำกัดของ single server ไม่ใช่ของ Hyper-V Lenovo Premier 24×7 4HR SLA — engineer ถึงที่ภายใน 4 ชั่วโมง + เก็บ server เก่าไว้เป็น standby
Application ไม่ทำงานบน VM ต่ำมาก HAOS และ Software ที่ใช้รองรับ Hyper-V อยู่แล้ว — Panacea-Repl ก็รันบน Hyper-V อยู่แล้วในปัจจุบัน ทดสอบ UAT ร่วมกับ Clinical ก่อน Go-live

ไม่กระทบการใช้งาน

Restore SQL Database ไป VM ใหม่, Convert VM อื่น, ตรวจสอบข้อมูลครบถ้วน
ทีม AYD ดำเนินการ — ไม่ต้องการ IT โรงพยาบาล ณ จุดนี้
ทดสอบร่วมกับ IT โรงพยาบาล (1–2 ชั่วโมง)
Login, ทดสอบ OPD/IPD workflow, ตรวจสอบ report, ยืนยันว่าข้อมูลถูกต้อง
