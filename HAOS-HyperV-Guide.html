Virtual Switch & Network Setup
💡 แนะนำ: SET (Switch Embedded Teaming) ใช้ SET แทน NIC Teaming แบบเดิม — SET รวม 2 NIC เข้า vSwitch โดยตรง ไม่ต้อง create team ก่อน รองรับ SR-IOV และ RDMA

Virtual Switch Design

vSwitch "VM-External"
External type | vmnic0 (25GbE) → VM Traffic + Host Management
ใช้ VLAN tagging แยก Management vs VM Network
vSwitch "VM-Storage"
Internal/Private type → สำหรับ VM-to-VM traffic ถ้าต้องการ (optional)
NIC 2 (vmnic1)
สำรองสำหรับ Backup traffic / อนาคตทำ SET ได้

PowerShell: Create Virtual Switch

  • สร้าง External vSwitch ผูกกับ NIC จริง
    New-VMSwitch -Name "VM-External" -NetAdapterName "Ethernet" -AllowManagementOS $true
    Engineer
  • Enable SR-IOV บน vSwitch (ถ้า Broadcom 57414 รองรับ)
    New-VMSwitch -Name "VM-External" -NetAdapterName "Ethernet" -EnableIov $true
    SR-IOV ลด latency สำหรับ VM network ได้ชัดเจน
    Engineerแนะนำ
  • ตั้ง VLAN ID สำหรับ Management NIC ของ Host
    Set-VMNetworkAdapterVlan -ManagementOS -VMNetworkAdapterName "Management OS" -Access -VlanId [MGMT_VLAN]
    IT
  • Enable VMQ (Virtual Machine Queue) สำหรับทุก VM NIC
    VMQ ปรับปรุง network throughput โดยการ distribute processing
    Set-VMNetworkAdapter -VMName "Panacea-DB" -VmqWeight 100
    Engineer
⚠️ ระวัง: Management NIC ของ Host ต้องไม่หายไปหลัง create vSwitch ถ้า set vSwitch ผิด Host จะ lose network connection — ทำผ่าน console (iDRAC/XCC) เสมอ ไม่ใช้ RDP

Storage Layout — Volumes สำหรับ Hyper-V
💡 Hyper-V ใช้ NTFS/ReFS Volumes แทน Datastore (ESXi) RAID 940-16i สร้าง logical disk → Windows เห็นเป็น Physical Disk → Format เป็น Volume

Volume Layout (แทน ESXi Datastore)

C: (Boot)
SATA RAID 1 → 480 GB → NTFS → Windows Server 2025 Host OS
D: Master Data
NVMe #1-4, RAID 10 → 6.4 TB → ReFS → VHDX ของ Master VM (OS + SQL Data + TempDB)
E: Master Log
NVMe #5-6, RAID 1 → 3.2 TB → ReFS → VHDX ของ Master VM (SQL Log เท่านั้น)
F: Shared
NVMe #7-8, RAID 1 → 3.2 TB → ReFS → VHDX ของ Repl+ELK, App, RPT-App
💜 ทำไมต้องใช้ ReFS แทน NTFS?
  • Block Cloning — copy VHDX เร็วกว่า NTFS มาก (zero data copy)
  • Auto-repair — ตรวจ corruption ได้เองโดยไม่ต้อง chkdsk
  • VHDX Performance — Hyper-V + ReFS + Fixed VHDX = I/O เร็วที่สุด
  • ⚠️ ReFS ไม่รองรับ compression, encryption, dedup — แต่สำหรับ SQL production ไม่ต้องการ feature เหล่านี้

VHDX Type: Fixed vs Dynamic

TypePerformanceSpaceแนะนำ

Differencing VHDXแย่ที่สุด—✗ ห้ามใช้กับ Production

Migration Strategy — ESXi → Hyper-V
🔴 Source server ใช้ ESXi — VM ทุกตัวเป็น VMDK format ไม่สามารถ Import เข้า Hyper-V ตรงๆ ได้ — ต้องผ่านขั้นตอน Discovery → Pre-migration → Convert → Verify ก่อนทุกครั้ง

ภาพรวม Migration Path

VMต้นทาง (คาดการณ์)Formatวิธี MigrationDowntime โดยประมาณ
Panacea-DB ESXi VM (หรือ Bare Metal) VMDK / Physical SQL Backup + Restore (แนะนำ) ~4-8 ชม.
Panacea-Repl+ELK ESXi VM VMDK StarWind V2V: VMDK → VHDX ~2-4 ชม. + conversion time
Panacea-App ESXi VM (หรือ Bare Metal) VMDK / Physical StarWind V2V หรือ Disk2VHD ~2-4 ชม.
Panacea-RPT-App ESXi VM (หรือ Bare Metal) VMDK / Physical StarWind V2V หรือ Disk2VHD ~2-4 ชม.

    Host Client → Summary → Version — กระทบ compatibility ของ export tools

    Engineer
  • ตรวจว่า VM มี Snapshot อยู่ไหม

  • ตรวจ VMDK format ของแต่ละ disk (Thin / Thick)

    EngineerIT

ขั้นตอนที่ 1 — Pre-Migration (ทำบน Source ESXi ทุกตัว)

⚠️ ต้องทำขั้นตอนเหล่านี้ก่อนทุกครั้ง — ถ้าข้ามจะเกิด BSOD หรือ boot loop ใน Hyper-V
  • Consolidate Snapshots ทุกตัวให้หมด
    Right-click VM → Snapshots → Consolidate — รอจนเสร็จสมบูรณ์ก่อนทำ step ต่อไป
    Engineerห้ามข้าม
  • Uninstall VMware Tools ออกจากทุก VM (ยกเว้น Panacea-DB ที่ใช้ SQL Backup)
    เข้า VM → Control Panel → Programs → Uninstall VMware Tools — ถ้าไม่ uninstall จะ conflict กับ Hyper-V Integration Services
    Engineerห้ามข้าม
  • ตรวจ Disk Partition Style — ต้องเป็น GPT (ไม่ใช่ MBR) สำหรับ Gen 2 VM
    เข้า VM → Disk Management → ดู Disk 0 Properties — ถ้าเป็น MBR ต้องแปลง: mbr2gpt /convert /allowFullOS แล้ว reboot
    Engineerสำคัญมาก
  • Shutdown VM ก่อน convert ทุกครั้ง
    ห้าม convert VM ขณะกำลังทำงาน (ยกเว้น StarWind Live Migration mode) — VMDK ที่ open อยู่อาจได้ข้อมูลไม่สมบูรณ์
    Engineer
  • ทำ Full SQL Backup ล่าสุดก่อนทุกอย่าง (สำหรับ Panacea-DB)
    เก็บไว้บน external storage — นี่คือ safety net ถ้า migration ล้มเหลว
    DBAสำคัญที่สุด

⚠️ Panacea-Repl+ELK, App, RPT-App — ใช้ StarWind V2V

VM เหล่านี้ไม่ใช่ SQL production ดังนั้น V2V conversion ยอมรับได้ — แต่ยังต้องทำ Pre-migration steps ให้ครบก่อน

  • [V2V] Copy VMDK files ออกจาก ESXi Datastore มาไว้บน Windows machine ที่ run StarWind
    ใช้ SCP / Datastore Browser / WinSCP เชื่อมต่อ ESXi โดยตรง — ต้องการ space เท่ากับขนาด disk
    Engineer
  • [V2V] Run StarWind V2V Converter: VMDK → Fixed VHDX
    เลือก "Local file" → input .vmdk → output path บน D:/E:/F: ตาม VM → เลือก Fixed size (ไม่ใช้ Dynamic)
    Engineer
  • [V2V] สร้าง VM ใหม่บน Hyper-V (Gen 2) แนบ VHDX ที่ convert แล้ว
    ตรวจสอบ Secure Boot setting — ถ้า VM เดิมไม่ได้ใช้ Secure Boot ให้ปิดก่อน boot ครั้งแรก
    Engineer
  • [V2V] Boot VM ครั้งแรก — ตรวจสอบ Windows ขึ้นปกติ
    ถ้า BSOD: ตรวจ Stop Code — 0x7B (INACCESSIBLE_BOOT_DEVICE) = driver SCSI ไม่โหลด → ต้อง inject driver ก่อน convert
    Engineerเตรียมรับมือ
  • [V2V] Install Hyper-V Integration Services และ uninstall VMware remnants
    Device Manager — ตรวจว่าไม่มี VMware device เหลือค้างอยู่ · IS จะถูก install อัตโนมัติผ่าน Windows Update
    Engineer
  • [V2V] ตั้งค่า Static Memory และปิด Dynamic Memory ใน VM Settings
    Engineer

#รายการที่ขาดจำเป็น?ทางออกค่าใช้จ่าย
1 Backup Solution — ไม่มี plan backup off-site Critical Windows Server Backup (ฟรี, basic) หรือ Veeam Community / NAKIVO ฟรี–ปานกลาง
2 External Backup Storage — ต้องมี destination นอก server Critical NAS, tape, cloud (Azure Backup), หรือ offsite disk ขึ้นอยู่กับ solution
3 UPS (Uninterruptible Power Supply) สูง APC / Eaton — ต้องรับ load 1300W PSU ×2 ~50K-150K THB
4 KVM / Console access นอกจาก iDRAC/XCC ปานกลาง iDRAC (XCC) ที่มาพร้อม SR650 เพียงพอแล้ว — แต่ควร config ก่อน install มีอยู่แล้ว
5 Windows Admin Center แนะนำ ดาวน์โหลดฟรีจาก Microsoft — ต้องมี machine สำหรับ WAC gateway ฟรี
6 SQL Server Enterprise license สำหรับ Replica (ถ้า readable) ขึ้นกับ decision ถ้า passive DR ไม่ต้อง | ถ้า readable ต้องซื้อ ~฿490K ถ้าต้องการ
7 Network Switch 25GbE — ถ้า switch ปัจจุบันเป็น 1GbE ขึ้นกับ infra ถ้า switch รองรับ 10/25GbE ผ่าน SFP+ ก็ใช้ได้ — ตรวจสอบก่อน แล้วแต่รุ่น
8 Anti-Virus สำหรับ Host + VMs แนะนำ Microsoft Defender (ฟรี, built-in WS2025) หรือ enterprise AV ฟรี–มีค่าใช้จ่าย

ความเสี่ยงและข้อควรระวัง (Hyper-V Specific)
#ความเสี่ยงระดับการป้องกัน
1 Host Reboot จาก Windows Update = VM ทุกตัว down
ต่างจาก ESXi ที่ update แยก		 High ปิด Auto Update บน Host · วางแผน maintenance window ทุกครั้ง · แจ้ง clinical team ล่วงหน้า
2 Dynamic Memory เปิดอยู่บน SQL VM
ถ้าลืมปิด SQL buffer pool จะถูก balloon		 High ตรวจสอบทุก VM ว่า Static Memory = ON และค่า Min = Max เสมอ
3 Checkpoint บน SQL VM
Checkpoint = SQL log chain break → restore ไม่ได้		 High ปิด Checkpoint ใน VM settings สำหรับ SQL VM · ใช้ SQL Backup แทน
4 NUMA Crossing
ถ้า VM ได้ RAM/CPU ข้าม NUMA node → latency เพิ่ม		 Medium ตั้งค่า NUMA topology ใน VM · Master DB ควร pin ไป Socket 0
5 P2V SQL Server ด้วย Disk2VHD ขณะ SQL ทำงาน
อาจได้ VHDX ที่ inconsistent		 High หยุด SQL Service ก่อน Disk2VHD · หรือใช้ Backup+Restore แทน P2V
6 Gen 1 vs Gen 2 VM Compatibility
Disk2VHD จาก MBR disk → ต้องแปลงเป็น GPT ก่อน Gen 2		 Medium ใช้ mbr2gpt /convert /allowFullOS บน bare metal ก่อน P2V
7 Host OS เป็น attack surface ใหญ่กว่า ESXi
Windows มีบริการมากกว่า ESXi kernel		 Medium ใช้ Server Core · ปิด role ที่ไม่ใช้ · เปิด Windows Firewall · update สม่ำเสมอ
8 VHDX Fixed ใช้เวลา create นาน
VHDX ขนาด 5 TB = pre-allocate นาน		 Low สร้าง VHDX ล่วงหน้าก่อนวัน migrate · บน ReFS เร็วกว่า NTFS มาก (Block Cloning)
9 Integration Services ไม่ install
VM จาก snapshot เก่าอาจมี IS version เก่า		 Low ตรวจสอบ IS version ใน Device Manager ของทุก VM หลัง import
10 ไม่มี hot spare drive (เหมือน ESXi plan) Medium Lenovo Premier 24×7 4HR SLA ที่มีอยู่ใน BOM — ตรวจสอบ activation

คำแนะนำเพิ่มเติม (Best Practices)

SQL Server บน Hyper-V — ตั้งค่าเพิ่มเติม

  • ปิด Hyper-V Time Synchronization Integration Service บน SQL VM
    SQL Server จัดการ time เอง — ถ้า Hyper-V sync time อาจ conflict กัน
    ปิดที่: VM Settings → Integration Services → ยกเลิก "Time synchronization"
    DBAสำคัญ
  • ใช้ SCSI Synthetic Adapter เท่านั้น (ไม่ใช้ IDE)
    Gen 2 VM บังคับ SCSI แล้ว — แต่ถ้า import VM เก่า Gen 1 ต้องตรวจสอบ
    Engineer
  • ตั้งค่า SQL max server memory ให้เหลือ RAM สำหรับ Windows OS ใน VM
    VM มี 240 GB → SQL max memory = 216 GB (เผื่อ 24 GB สำหรับ Windows)
    DBA
  • ตั้งค่า Disk Queue Length สำหรับ VHDX
    Storage QoS: ตั้งค่า MaximumIOPS เพื่อป้องกัน VM ใดใด้โมนอป Pool 3 (Shared)
    Engineerแนะนำ

Hyper-V Host Best Practices

  • ใช้ Windows Admin Center แทน Hyper-V Manager แบบเก่า
    WAC รองรับ browser-based management, VM monitoring, Performance counters ใน UI เดียว
    ITแนะนำ
  • ตั้งค่า Hyper-V Host Automatic Stop Action เป็น "Save" หรือ "Shutdown"
    ถ้า Host ปิดตัวกะทันหัน — "Shutdown" ดีกว่าสำหรับ SQL (graceful)
    Engineer
  • Monitor Hyper-V Performance Counters สำคัญ
    Hyper-V Hypervisor Virtual Processor\% Total Run Time
    Hyper-V Virtual Storage Device\Read Latency
    Hyper-V Virtual Storage Device\Write Latency
    IT
  • ทำ VM Export (Full backup ระดับ VM) อย่างน้อยสัปดาห์ละครั้ง
    Hyper-V Export = backup ระดับ VM ทั้งก้อน — เก็บไว้ external storage
    ITDBA
  • เก็บ bare metal เดิมไว้เป็น DR อย่างน้อย 3-6 เดือน
    ถ้า server ใหม่มีปัญหา สามารถ fallback กลับได้ — เหมือน ESXi plan
    ITPM

Backup Strategy สำหรับ Hyper-V

ระดับเครื่องมือความถี่Destination
SQL Transaction Log SQL Server Agent ทุก 15-30 นาที VM local → copy ไป external
SQL Full Backup SQL Server Agent ทุกคืน External storage / NAS
VM Backup (Hyper-V) Veeam Community / NAKIVO / Windows Server Backup ทุกวัน External storage
Host OS Backup Windows Server Backup หลัง config เปลี่ยน Network share
✅ สรุปคำแนะนำหลัก
  • ใช้ Server Core สำหรับ Hyper-V Host — ไม่ใช้ Desktop Experience
  • ใช้ Static Memory + ปิด Dynamic Memory บนทุก VM โดยเฉพาะ SQL
  • ใช้ Fixed VHDX บน ReFS — ไม่ใช้ Dynamic VHDX และไม่ใช้ NTFS
  • ปิด Checkpoint บน SQL VM — ใช้ SQL Backup เท่านั้น
  • ปิด Time Synchronization Integration Service บน SQL VM
  • ใช้ SQL Backup + Restore แทน Disk2VHD สำหรับ Panacea-DB
  • วางแผน Maintenance Window ให้ชัดเจนก่อน Host Update ทุกครั้ง
