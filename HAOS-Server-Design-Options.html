🎯 บริบทและเป้าหมายโครงการ

ปัญหาเดิม: HAOS (HIS ของรพ.) ช้า เนื่องจาก I/O contention บน shared disk ของ bare metal server ที่รัน 4 VM ใช้ storage pool ร่วมกัน

เป้าหมายโครงการ: ย้าย 4 VM ไป server ใหม่ โดยใช้ VM snapshot restore (ไม่ใช่ reinstall) พร้อม ออกแบบ disk pool แยกตาม workload เพื่อแก้ปัญหา I/O ให้จบ

⚖️ กฎเหล็กของโครงการนี้ ห้ามแบ่ง disk pool ให้ workload I/O หนักใช้ร่วมกัน — เป็น root cause ของปัญหาเดิมที่ลงทุนแก้อยู่ หาก design ใหม่ยังแชร์ pool ก็จะเจอปัญหาเดิมซ้ำ

🚨 ความเสี่ยงและสมมติฐานที่ต้องยอมรับ

ความเสี่ยงของ design ที่แนะนำ (β-v2)

# Risk ระดับ Mitigation
1 Master pool capacity ตึง ถ้า DB โต >10%/ปี จะเต็ม 6.4TB ในปี 2-3 High ยืนยัน growth rate กับ DBA; เตรียมแผน online migration ถ้าใกล้เต็ม
2 Single server = No HA server ตัวเดียวตาย HIS down ทั้งระบบ High เก็บ bare metal + vSphere เดิมเป็น DR/standby อย่างน้อย 3-6 เดือน หลัง stable
3 ไม่มี hot spare drive — ต้องพึ่ง Lenovo Premier 24×7 4HR SLA Medium SLA ครอบคลุมอยู่ใน BOM #10 แล้ว; ตรวจสอบ contract activation
4 Replica+ELK+App+Report share pool — workload burst อาจ interfere กัน Medium Monitor IOPS per workload; ถ้าเจอ contention ย้าย Report ไป off-peak
5 Backplane config ยังไม่ confirm — ถ้าไม่ใช่ AnyBay อาจต้อง rework cabling Medium ขอ Config ID + diagram จาก Lenovo ก่อน receive
6 RAM headroom เหลือเพียง 16 GB หลัง reallocation — vMotion / burst อาจ tight Low Monitor RAM pressure; ถ้าจำเป็นลด Master เหลือ 224 GB เพิ่ม buffer เป็น 32 GB
7 940-16i Tri-Mode = x1 lane per NVMe (ไม่เต็ม x4) → throughput bottleneck ที่ controller Low HAOS เป็น OLTP เน้น IOPS ไม่ใช่ throughput — impact ต่ำ

สมมติฐานที่ต้องเป็นจริง (Pre-conditions)

# สมมติฐาน ถ้าผิดสมมติฐาน
1 DB growth rate ≤ 10% ต่อปี ต้อง redesign → ต้องขอเพิ่ม NVMe drive 2 ลูก
2 Replica = passive DR (ไม่ใช่ readable secondary) ต้องซื้อ SQL Enterprise license เพิ่ม 1 ตัว (~$14K)
3 ELK retention < 1 TB ต้องวางแผน archive ไป external storage
4 Backplane = AnyBay (ต่อผ่าน 940-16i ได้ครบ) ถ้าเป็น NVMe direct-attach → 940-16i คุม NVMe ไม่ได้ ต้อง redesign
5 ยอมรับความเสี่ยง "ไม่มี hot spare" ด้วย 4HR SLA ถ้าไม่ยอม → ต้องขอเพิ่มไดรฟ์สำหรับ spare

✅ สิ่งที่ผู้บริหารต้องตัดสินใจ

  • 1. ยอมรับ Option β-v2 เป็น target design หรือไม่ เปรียบเทียบ β vs β-v2 แล้วเลือก → β-v2 แนะนำเพราะ SQL log isolation
    ผู้มีอำนาจตัดสิน: Hospital Exec + IT Manager
  • 2. DB growth rate เฉลี่ยต่อปี? ถ้า ≤10% → β-v2 ปลอดภัย 3 ปี | ถ้า >10% → ต้องพิจารณาเพิ่มไดรฟ์
    ต้องข้อมูลจาก: DBA / HIS team
  • 3. Replica = passive DR หรือ readable secondary? กระทบงบ SQL license ~$14K/core × 8 cores
    ต้องข้อมูลจาก: DBA + Finance
  • 4. เก็บ bare metal + vSphere เดิมเป็น DR standby? ถ้าเก็บ = ต้นทุน maintenance + license เดิม | ถ้าปลด = ไม่มี failover
    ผู้มีอำนาจตัดสิน: Hospital Exec
  • 5. ยอมรับ RAM headroom 16 GB หรือเพิ่ม RAM? เพิ่ม 128 GB อีก 2 stick = ~300K THB | ไม่เพิ่ม = monitor ใกล้ชิด
    ผู้มีอำนาจตัดสิน: IT Manager + Finance
  • 6. Downtime window สำหรับ cutover — ยอมรับกี่ชั่วโมง? ส่งผลต่อ migration strategy (live sync vs cold copy) + rollback window
    ผู้มีอำนาจตัดสิน: Hospital Exec + Clinical team
  • 7. Backup + DR strategy (ไม่อยู่ใน BOM) server ใหม่ไม่มี plan backup off-site — ต้องจัดทำแผนเพิ่ม
    ผู้มีอำนาจตัดสิน: IT Manager + DBA + Compliance

9. Post-Install Validation Checklist

  • ☐ Run IOmeter / CrystalDiskMark บน VM → IOPS target: >200K random read/write (NVMe RAID 10)
  • ☐ Run SQLIOSim บน Master → ไม่มี error, latency <5ms
  • ☐ Verify RAM: SQL buffer pool โตถึง ~200 GB หลัง warmup
  • ☐ Verify: Log write latency <1ms ตอน idle
  • ☐ Backup plan testing — full + log backup restore successful
  • ☐ Monitoring agent install (Zabbix / PRTG / whatever รพ. ใช้)
  • ☐ Document baseline metrics (TPS, IOPS, CPU%, RAM%, latency)
🔴 CRITICAL — ห้าม implementer ทำ (ต้องขออนุมัติ PM)
  • สร้าง RAID configuration ต่างจาก spec นี้
  • รวม datastore จาก multiple pool เข้าด้วยกัน
  • วาง VM disk ข้าม datastore (เช่น Master Data ไปอยู่ Pool 3)
  • เปลี่ยน RAID write policy เป็น Write Through (กระทบ perf หนัก)
  • Enable disk cache บน drive (ผ่าน controller settings)
