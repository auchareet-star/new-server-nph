  • ยืนยัน Replica role — passive DR หรือ readable secondary?
    passive DR = ใช้ license ที่มีอยู่ได้ | readable secondary = ต้องซื้อ SQL Enterprise เพิ่ม ~$14K/core × 8 cores
    DBAผู้บริหาร
  • ตัดสินใจเก็บ bare metal เดิมเป็น DR standby หรือปลด
    เก็บ = มี fallback ถ้า server ใหม่มีปัญหา (แนะนำอย่างน้อย 3-6 เดือน) | ปลด = ไม่มี failover แต่ประหยัด license + maintenance
    ผู้บริหาร
  • ยืนยัน Downtime window สำหรับ cutover — ยอมรับกี่ชั่วโมง?
    กระทบ migration strategy: live sync (downtime สั้น) vs cold copy (downtime นาน) และ rollback window
    ผู้บริหารIT Manager

Post-Install Validation — ต้องผ่านทุกข้อก่อน Go-Live ▼
  • Run IOmeter / CrystalDiskMark บน Master VM
    Target: >200K IOPS random read/write (NVMe RAID 10 ควรทำได้สบาย)
    EngineerDBA
  • Run SQLIOSim บน Master VM
    ต้อง: ไม่มี error + latency <5ms
    DBA
  • Verify SQL buffer pool โตถึง ~200 GB หลัง warmup
    ใช้ SELECT physical_memory_in_use_kb FROM sys.dm_os_process_memory
    DBA
  • Verify Log write latency <1ms ตอน idle
    ดูจาก sys.dm_io_virtual_file_stats หรือ Windows Performance Monitor
    DBA
  • ตรวจสอบ SQL Log file (.ldf) อยู่บน DS-MASTER-LOG (Pool 2) ถูกต้อง
    ตรวจด้วย SELECT name, physical_name FROM sys.master_files
    DBA
  • ทดสอบ Backup + Restore (full + log backup) สำเร็จ
    รวมถึงทดสอบ point-in-time restore ให้ทำได้จริง
    DBA
  • ตรวจสอบ Replication sync ระหว่าง Master → Replica ปกติ
    Lag ยอมรับได้ <10 วินาที ในสภาวะปกติ
    DBA
  • Install Monitoring Agent บนทุก VM (4 VMs)
    Zabbix / PRTG / ระบบที่โรงพยาบาลใช้ — ต้องมี alert: disk full, high IOPS, replication lag
    ITEngineer
  • Document baseline metrics ก่อน cutover
    TPS, IOPS per pool, CPU%, RAM%, log write latency, replication lag — เก็บไว้ compare หลัง go-live
    DBAIT
  • UAT กับ Clinical team ก่อน cutover จริง
    ทดสอบ scenario หลัก: OPD registration, IPD admission, dispensing, report generation
    ITClinical team
✅ ผ่านทุกข้อ = พร้อม Go-Live หลัง go-live ให้ monitor DS-SHARED อย่างใกล้ชิด 1 สัปดาห์แรก เพราะ Replica+ELK+App+Report share pool เดียวกัน ถ้าเกิด IOPS contention ให้ย้าย Report ไป off-peak schedule
!
สิ่งที่ Implementer ห้ามทำโดยเด็ดขาด (ต้องขออนุมัติ PM) ▼
  • สร้าง RAID configuration ต่างจาก spec ที่กำหนด
  • รวม datastore จาก multiple pool เข้าด้วยกัน
  • วาง VM disk ข้าม datastore ผิด (เช่น Master Log ไปอยู่บน DS-MASTER-DATA)
  • เปลี่ยน RAID write policy เป็น Write Through (กระทบ performance หนัก)
  • Enable disk cache บน drive ผ่าน controller settings
